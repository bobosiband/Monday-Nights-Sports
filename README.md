# Monday Night Sports 🏆

A web and mobile app for managing college Monday night sports competitions. Built to handle live scoring, league standings, fixture scheduling, and college team management — designed to last well beyond the students who built it.

---

## What this app does

Every Monday, colleges compete across multiple sports. This app is the central hub for everyone involved:

- **Students** can check upcoming fixtures, follow live scores, and track their college's standing in the league — no account needed.
- **Event managers** (one per college) can create and manage fixtures, configure sport settings, and record match results.
- **Score operators** (sideline staff) can run a live scoring screen during a match — tracking goals, time, and match events in real time.

The app is designed to support **400+ concurrent viewers** with no login required for public access, while keeping college account management simple and secure.

---

## Key features

### For everyone (public, no login)
- View upcoming and past fixtures
- Live scores during matches (auto-refreshing)
- League standings tables — styled appropriately per sport (Premier League style for soccer, NBA style for basketball, configurable for others)
- College profiles with team colours, season stats, and head-to-head history
- Fixture calendar — weekly view of all Monday matches

### For event managers (college accounts)
- Create and manage fixtures between colleges
- Auto-generate a round-robin schedule for the season (9 weeks, Week 6 skipped as flex week)
- Configure sport settings: period count, period duration, scoring increments, points system, tiebreaker rules
- Override or adjust auto-generated fixtures
- Private match notes (referee incidents, postponements, etc.)

### For score operators (sideline)
- Live scoring screen — one colour per team, large +/− buttons
- Running match timer with pause/resume
- Period management (end half, start next, extra time)
- Match event log (goals, time of each event)
- Undo last action
- Penalty shootout tracker (for knockout stages)
- Works offline — queues updates and syncs when connection returns

### Sport configuration (fully flexible)
Each sport season is configured by the event manager before it starts:
- Number and duration of periods
- Scoring increments (e.g. +1 for soccer, +1/+2/+3 picker for basketball, custom for others)
- Standings table columns and ordering
- Win/draw/loss points values
- Tiebreaker rules
- Extra time rules (golden goal, timed periods, or straight to penalties)

## Tech overview

> This section will be updated as architecture decisions are made. For now, treat this as a starting point for discussion.

**Frontend** — React (web) + React Native or a PWA for mobile. The public-facing app should feel fast on mobile since most students will use it on their phones at the game.

**Backend** — REST API (Node.js/Express or similar). Handles fixture management, score updates, and college accounts.

**Database** — PostgreSQL. Relational data fits well here (colleges, fixtures, sports, scores, standings).

**Real-time** — WebSockets or server-sent events for live score updates to public viewers during a match.

**Auth** — JWT-based sessions for college accounts. Score operators use a short-lived match PIN (generated by the event manager before the game).

**Offline** — Service worker on the scoring screen to queue score updates locally when offline, syncing when reconnected.

## Project structure (expected but could change)

The project is split into two top-level folders — `frontend/` and `backend/` — so they can be developed, deployed, and owned independently.

```
monday-night-sports/
├── frontend/                   # Everything the user sees (React)
│   ├── src/
│   │   ├── pages/
│   │   │   ├── public/         # Public viewer pages (fixtures, standings, profiles)
│   │   │   ├── manager/        # Event manager portal (fixtures, sport config)
│   │   │   └── scoring/        # Live scoring screen
│   │   ├── components/         # Shared UI components
│   │   ├── hooks/              # Shared React hooks (e.g. useLiveScore, useAuth)
│   │   └── services/           # API client — all calls to the backend go through here
│   ├── public/                 # Static assets (icons, fonts)
│   ├── .env.example
│   └── package.json
│
├── backend/                    # API server (Node.js/Express)
│   ├── src/
│   │   ├── routes/             # API endpoint definitions
│   │   ├── controllers/        # Request handlers (thin — call services, return responses)
│   │   ├── services/           # Business logic (standings calc, round-robin gen, etc.)
│   │   ├── models/             # Database models / query helpers
│   │   └── sockets/            # Real-time score broadcast (SSE or WebSockets)
│   ├── database/
│   │   ├── migrations/         # Schema changes over time (run in order, never edited)
│   │   └── seeds/              # Sample data for development
│   ├── .env.example
│   └── package.json
│
└── docs/                       # Project-wide documentation
    ├── planning.md             # Sprint-by-sprint dev plan
    └── decisions/              # Architecture decision records
```

> **Why split?** Frontend and backend have different dependencies, different deployment targets, and are often worked on by different people at the same time. Keeping them separate prevents dependency conflicts and makes it clear where a piece of code belongs.

## Getting started (development)

> Full setup instructions will be added once the stack is confirmed.

You'll need to run the frontend and backend in separate terminals.

**1. Clone the repo**

```bash
git clone https://github.com/your-org/monday-night-sports.git
cd monday-night-sports
```

**2. Set up and run the backend**

```bash
cd backend

# Install dependencies
npm install

# Start the backend dev server (default: http://localhost:3000)
npm run dev
```

**3. Set up and run the frontend**

```bash
# In a new terminal tab
cd frontend

# Install dependencies
npm install

# Set up environment variables
cp .env.example .env
# Set VITE_API_URL=http://localhost:3000 (or whatever port the backend runs on)

# Start the frontend dev server (default: http://localhost:5173)
npm run dev
```

## Environment variables (But could be different depending on what Stackframes we decide to use)

**`backend/.env`**

| Variable | Description |
|---|---|
| `DATABASE_URL` | PostgreSQL connection string |
| `JWT_SECRET` | Secret for signing auth tokens |
| `PORT` | Port the API server runs on (default: 3000) |
| `WS_PORT` | Port for WebSocket server (default: 3001) |
| `NODE_ENV` | `development` or `production` |

**`frontend/.env`**

| Variable | Description |
|---|---|
| `VITE_API_URL` | URL of the backend API (e.g. `http://localhost:3000`) |
| `VITE_WS_URL` | URL of the WebSocket/SSE server (e.g. `http://localhost:3001`) |
